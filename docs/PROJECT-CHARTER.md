## 1. ビジョン

MacBook 上で並行稼働する Codex セッションの状態を、一つのローカル画面で即座に把握できる状態を実現する。開発者が各ターミナルを巡回せず、稼働中・入力待ち・終了済みのセッションを区別して次の操作を判断できるようにする。

## 2. ビジネスゴール

| # | ゴール | 測定指標 |
|---|--------|---------|
| 1 | 単一MacBook上のCodexセッションを状態別に一画面で把握できるようにする | Phase 1の受け入れ確認で、稼働中・入力待ち・終了済みの各状態を一覧画面で区別して表示できる |
| 2 | 最大10件のセッション状態を短時間で最新化する | 起動後3秒以内に一覧を表示し、5秒ごとに状態を更新する。取得失敗・未知状態は5秒以内に明示し、終了済みとして扱わない。 |

## 3. 対象ユーザー / ペルソナ

| ペルソナ | 役割 | 主な目的 |
|---------|------|---------|
| Primary: 並列開発を行う個人開発者 | 自身のMacBookで複数のCodexセッションを実行する | 各セッションの状態を一画面で把握し、入力待ちの対応順を判断する |
| Secondary: 該当なし | — | Phase 1は自分のみ・MacBook 1台のみを対象とする |
| Negative: 複数ユーザーを監督する管理者、複数MacBookを管理する利用者 | チームや複数端末の状態を集約する | Phase 1では対象外とする |

## 4. Phase ロードマップ

| Phase | 名称 | スコープ概要 | 目標時期 |
|-------|------|------------|---------|
| Phase 1 | ローカルセッション可視化 | 単一MacBook上のローカルCodexセッションを、稼働中・入力待ち・終了済みとして一画面に一覧表示する。ローカルログとプロセス情報を読み取る。 | 2026-09-01 |
| Phase 2 | 将来候補（未着手） | 未計画 | 未計画 |
| Phase 3 | 将来候補（未着手） | 未計画 | 未計画 |

Phase 2以降のスコープは、Phase 1完了レビューでユーザーが再計画する。再計画では、Phase 1の最大10セッションに対する初回表示時間・更新間隔・状態取得失敗率・CPU利用率を判断材料とする。Codex Remoteのセッション可視化および複数MacBookの可視化は、Phase 1の対象外であり、将来の採否も未決定である。

## 4.1 スコープ外

以下はこのプロジェクトの対象外とする。

- Codex Remoteのセッション取得・表示
- 複数MacBookまたはチームのセッション集約
- セッション本文、プロンプト、応答内容の保存・表示
- ローカル端末外への状態データ送信
- アプリ終了後に残る状態・時刻・作業ディレクトリ名の保存

## 5. 非機能要件（6 分類）

| 分類 | 定量目標（レンジ可） | 計測方法 | 優先度 |
|------|-------------------|---------|--------|
| **可用性**（稼働率, RTO, RPO, 冗長構成） | 稼働率目標は設定しない。アプリ再起動後30秒以内に、状態または状態取得失敗を画面へ表示する。RPOは0（永続データを持たない）。 | アプリ再起動試験で、起動から画面表示までを計測する。 | MUST |
| **性能・拡張性**（応答時間, スループット, 同時接続数） | 最大10セッションを対象に、起動後3秒以内に一覧を表示し、5秒ごとに状態を更新する。取得失敗・未知状態は5秒以内に明示し、終了済みとして扱わない。 | 10セッションのE2E試験で初回一覧表示時間、更新間隔、未知・失敗状態の表示時間を計測する。 | MUST |
| **運用・保守性**（監視, バックアップ, 障害検知, 保守時間帯） | 読取り元ログを変更・複製・キャッシュ・送信しない。状態取得失敗を5秒以内に画面上で検知可能にする。バックアップは不要（永続データなし）。 | 意図的に読取り不能・未知状態を作り、画面表示とデータ残存をE2E試験で計測する。 | MUST |
| **移行性**（移行量, ダウンタイム, リハーサル） | 新規開発であり、移行対象データは0件、移行ダウンタイムは0分。 | リリース時に永続データ・移行手順が不要であることを確認する。 | MUST |
| **セキュリティ**（認証方式, アクセス制限, 暗号化, 監査ログ） | 127.0.0.1および::1のみでlistenし、ローカル証明書によるHTTPSで画面・状態取得APIを提供する。CORSで他originを許可せず、外部通信・テレメトリを既定で発生させない。セッション本文を取得・保存しない。 | loopback以外からの接続拒否、HTTPS強制、CORS、外部通信なし、終了後のデータ残存なしをE2E・ネットワーク試験で確認する。 | MUST |
| **環境・エコロジー**（設置環境, 電源, 廃棄基準） | 新規のクラウド・専用ハードウェアを使用しない。最大10セッションを5秒更新で5分間継続したときのアプリCPU平均利用率は5%以下とする。計測時は他の負荷試験を実行しない。 | 実行構成、外部インフラ利用の有無、上記条件でのCPU平均利用率を計測する。 | MUST |

### NFR 方針

| カテゴリ | 方針 | 根拠 |
|---|---|---|
| Performance / Availability | Google SREのSLI/SLO/RTO/RPO用語を採用し、具体値は§5を正とする。 | 初回表示・更新・復旧を測定可能にするため。 |
| Scalability | 水平スケールは不採用とする。 | 単一MacBook・localhost限定で、クラウド環境を使用しないため。 |
| Security 認証 | OAuth 2.0 / OIDCは不採用とする。 | 単一MacBook上の自分のみがlocalhostで利用し、アプリのユーザー認証を提供しないため。 |
| Security 脅威 | STRIDEを採用し、ローカルログ・プロセス情報を信頼しない入力として扱う。 | 入力改ざん、ログ内容の表示によるXSS、localhost API露出を設計時に検査するため。 |
| Security 既知リスク | OWASP Top 10（最新版）を採用する。OWASP API Security Top 10（最新版）は不採用とする。 | Web UIを提供するため前者を採用し、外部公開APIを提供しないため後者は不採用とする。 |
| Security 暗号化 | TLS 1.2+を採用する。ローカル証明書の発行・信頼手順と、未信頼または期限切れ時に状態取得を開始しない挙動を実装設計で定義する。永続データを持たないため保存データへのAES-256適用は発生しない。 | ブラウザとlocalhostアプリの間でも状態データが通信するため。 |
| Maintainability | Test PyramidとSOLID原則を採用する。 | TypeScriptによるアプリケーション実装を行うため。 |
| Observability | Three Pillars + OpenTelemetryは不採用とする。 | ローカル単一端末でのPhase 1であり、本番クラウド運用を行わないため。状態取得失敗はUIで明示する。 |
| Compliance | NIST CSF、GDPR、CCPA、HIPAA、PCI-DSS、SOC 2、ISO 27001は不採用とする。 | 規制対象データ、決済、医療、EU・カリフォルニア展開、B2B SaaSを扱わないため。 |
| Operability | DORA 4メトリクスを採用し、GitHub Actionsの実行履歴からリリースごとに確認する。Progressive Deliveryは不採用とする。 | GitHub ActionsによるCI/CDを採用する。クラウド本番運用を行わないため段階的デプロイは不要である。 |
| Supply chain | pnpm lockfileを固定し、Dependabotによる依存更新とCIでの依存性検査を行う。SBOM（CycloneDX / SPDX）は不採用とする。 | publicリポジトリだがOSS配布・セキュリティ規制対応を採用していないため。 |
| Accessibility | キーボード操作、色だけに依存しない状態表示、主要画面でWCAG 2.1 AAのコントラストを満たす。 | Web UIとしてWCAG 2.1を採用するため。 |

## 6. 制約事項

- 技術的制約: TypeScript、Next.js App Router、Node.js LTS、pnpm、Vitest、Playwrightを採用する。Codex CLIのローカルログおよびプロセス情報のみを状態取得元として利用する。
- ビジネス制約: Phase 1の目標日は2026-09-01である。Codex Remoteおよび複数MacBook管理は対象外とする。
- リソース制約: 利用者は自分のみ、対象端末はMacBook 1台のみである。

## 7. 前提条件

- Codex CLIが対象MacBookで稼働し、ローカルログまたはプロセス情報を読み取れる。
- ダッシュボードはlocalhostで起動し、外部ネットワークへの状態データ送信を行わない。
- 状態データはメモリのみで扱い、アプリ終了時に消去する。

## 8. リスク

| リスク | 影響度 | 発生確率 | 対策 |
|-------|-------|---------|------|
| Codex CLIのログ形式またはプロセス情報が変更され、状態を判定できなくなる | 高 | 中 | ログ読取権限エラー、プロセス列挙エラー、形式変更を「取得失敗」または「未知状態」として5秒以内に表示し、終了済みとして扱わない。 |
| 状態分類の定義がCodex CLIの実際の挙動と一致しない | 高 | 中 | 稼働中・入力待ち・終了済みの判定根拠をEpic Specで検証可能な条件として確定し、根拠を得られない場合は未知状態として表示する。 |
| 2026-09-01までの期間が短く、Phase 1の受け入れ条件を満たせない | 高 | 高 | Phase 1の範囲を§4.1の対象外に固定し、機能追加をPhase 1へ入れない。 |
| ローカルログまたは作業ディレクトリ名に機密情報が含まれる | 高 | 中 | セッション本文を取得・表示・保存せず、状態データはメモリのみで扱う。 |

## 9. アーキテクチャ方針

| 項目 | 方針 |
|------|------|
| 構成 | MacBook上で起動するNext.js App RouterのローカルWebアプリ。127.0.0.1および::1だけでlistenし、ブラウザはローカル証明書を用いたHTTPSのlocalhostへ接続する。 |
| パターン | 単一プロセスのモジュラーモノリス。UIとローカル状態取得用のサーバー処理を同一アプリに配置する。 |
| データフロー | ブラウザ → HTTPSのlocalhost Next.jsアプリ → Codex CLIのローカルログ／プロセス情報 → 状態をメモリ上で整形 → ブラウザへ一覧表示。読取り元ログを変更・複製・キャッシュ・送信しない。 |
| 外部連携 | Codex CLIのローカルログおよびプロセス情報の読取りのみ。外部API・クラウドサービス・Codex Remoteとの連携は行わない。 |

| CI/CD | GitHub Actions | リポジトリで採用済みのCI/CD基盤。 |
| パッケージマネージャー | pnpm（latest stable） | ユーザー承認済みの推奨スタック。 |
| ツールバージョン管理 | mise | aidd-fwの固定方針。 |
| インフラ / クラウド | MacBook上のlocalhost。クラウド不使用。 | 完全ローカル限定というユーザー制約に従うため。 |
